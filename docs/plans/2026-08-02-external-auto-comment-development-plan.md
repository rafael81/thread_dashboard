# 타인 게시글 자동댓글 개발 계획

## 목적과 범위

`@terafabXai` 계정으로 **다른 사람이 작성한 원글**에만 자동댓글을 작성한다.
내 게시글의 댓글에 대댓글을 다는 작업, Threads 발굴/예약 게시, 자동 하트는 이
파이프라인과 별도 작업으로 유지한다.

이 계획은 실제 게시량을 늘리기 전에 대상 선정, 문맥 근거, 품질, 중복 방지,
X 게시 실패 복구를 각각 독립적으로 검증할 수 있게 만드는 것을 목표로 한다.

### 고정 운영 원칙

- 원문 URL과 원문 문맥이 없으면 댓글을 만들거나 게시하지 않는다.
- Grok 문맥 분석이 확인되지 않은 항목은 Gemini 결과가 있어도 게시하지 않는다.
- Gemini 검수와 독립 최종 판정을 모두 통과한 초안만 게시 대기열에 넣는다.
- 대상 URL 단위로 한 번만 게시한다. API 확인/DOM 확인이 불확실하면 재게시하지
  않고 `verification_required`로 전환한다.
- 일반 자동댓글은 같은 작성자에게 KST 날짜 기준 하루 최대 2건이다.
- 민감 주제, 광고·사기성 게시물, 댓글 유도·공격성 문맥, 근거 없는 사실 단정은
  자동댓글 대상에서 제외한다.
- 실제 X 조작 전에는 항상 `@terafabXai` 로그인 상태를 검증한다.

## 목표 아키텍처

```text
FxTwitter 팔로잉/백로그
        |
        v
[대상 정규화·중복/작성자 한도·안전 필터]
        |                         \n+        | reject/hold -----------> 사유와 KST 시각을 대시보드에 기록
        v
 [Grok: 원문 URL별 문맥+초안]  (병렬, 항목별 독립 세션)
        |
        v
 [Gemini: 검수·재작성 + 독립 최종 판정]
        |
        v
 [결정적 품질 게이트] --> quarantine (게시하지 않음)
        |
        v
 [영속 게시 대기열] -- 단일 consumer --> [X writer 9238]
        |                                      |
        |                                      v
        +<-- API/DOM 게시 검증 <----- reply URL / 불확실 상태
        |
        v
 commentHistory · 작성자 일일 한도 · 운영 지표
```

현재 구현에는 위의 대부분이 있으며, 앞으로는 각 상태를 섞지 않는 것이 핵심이다.
후보(`commentTargetBacklog`), 준비 중 초안, 게시 가능 초안(`pendingCommentPosts`),
게시 성공 이력(`commentHistory`), 재확인 필요 항목을 서로 다른 상태로 관리한다.
실패 메시지나 빈 원문을 초안/게시 텍스트로 승격하지 않는다.

## 단계별 개발 계획

### 0. 계약과 데이터 상태를 먼저 고정

1. 각 레코드에 `targetUrl`, `targetId`, `authorHandle`, `source`, `stage`,
   `createdAt`, `updatedAt`, `attempts`, `nextAttemptAt`, `lastError`를 공통으로 둔다.
2. 상태는 `candidate`, `context_ready`, `review_ready`, `pending_post`, `posted`,
   `held`, `quarantined`, `verification_required`만 사용한다. UI 문구와 내부 상태를
   분리해 표기 오류를 막는다.
3. 영속 큐를 갱신할 때는 URL을 idempotency key로 사용한다. 재시작 후에도 pending,
   작성자별 예약 수, 마지막 시도 시각이 그대로 복원돼야 한다.
4. 기존 JSON 상태 저장소의 원자 저장·복구를 시험한다. 큐 수가 커져 잠금 경합이나
   손상 위험이 확인될 때만 SQLite 전환을 별도 마이그레이션으로 진행한다.

완료 조건: 같은 URL이 여러 수집 경로에서 들어와도 하나의 레코드만 남고, 서버
재시작 뒤에도 게시 보류/재시도 정책이 바뀌지 않는다.

### 1. 대상 수집과 선정 분리

1. FxTwitter 팔로잉 타임라인과 기존 backlog를 주 수집원으로 사용한다. X 홈 DOM은
   후보가 부족할 때만 명시적인 보강 작업으로 두며, 기본 경로에서는 사용하지 않는다.
2. 수집 직후 FxTwitter status API로 원글 여부, 본문, 작성자, 미디어/인용문 메타를
   다시 확인한다. 답글, 비어 있는 본문, 금칙 주제, 광고성/사기성 후보는 즉시 제외한다.
3. 최신성, 작성자별 KST 일일 잔여량, 이미 처리한 URL, 후보 안전 점수를 기준으로
   우선순위를 계산한다. 같은 작성자에 집중하지 않도록 한도 이전에도 분산 정렬한다.
4. 후보 부족·API 404/429·네트워크 오류는 후보 자체의 영구 실패와 구분한다.
   일시 오류는 지수 backoff 후 다시 확인하고, 금칙/중복/한도는 명시적 hold 사유로 남긴다.

완료 조건: API 실패나 단순 수집 오류가 댓글 본문으로 흘러가지 않고, 한도·중복·제외
사유가 각각 집계된다.

### 2. 문맥·초안·검수를 병렬 준비 단계로 구성

1. Grok은 원글 URL 하나씩만 받아 원문/첨부 미디어 문맥과 후보 초안을 함께 반환한다.
   항목별 세션을 최대 5개 병렬로 돌리되, 서로 다른 원문 문맥을 섞지 않는다.
2. Grok 결과에는 원문 요약, 근거 키포인트, 미디어 파악 여부, 초안, 공급자/요청 ID를
   구조화해 저장한다. 한도·로그인·타임아웃은 `retryable` 여부와 재시도 시각을 함께 저장한다.
3. Gemini는 준비된 항목을 검수/재작성한 뒤, 독립 최종 판정에서 문맥 일치·근거 문구·
   일반론/클리셰·언어 품질을 평가한다. 최종 판정이 없거나 기준 점수 미달이면 게시하지 않는다.
4. 결정적 품질 게이트는 길이, 금칙어, 과장·법률/의학/기술 단정, 근거 없는 감각·시간
   묘사, 원문 주체 불일치를 차단한다. 프롬프트 수정은 이 게이트의 실패 사유 통계를
   근거로만 적용한다.

완료 조건: Grok 실패/한도, Gemini 실패, 품질 탈락이 서로 다른 큐 상태와 대시보드
사유로 보이며, 어느 경우도 X writer로 전달되지 않는다.

### 3. 단일 writer와 게시 검증을 견고화

1. 초안 준비는 병렬이지만 X 게시만 전용 Chrome writer(9238) 한 개가 FIFO로 처리한다.
   이는 동일 계정의 게시 순서와 X UI/세션 충돌을 막기 위한 고정 제약이다.
2. 각 게시 직전 재검증: 대상 URL 형식, 중복 이력, 작성자 일일 한도, Grok 확인,
   Gemini 최종 통과, 전역 pause/quiet 모드, `@terafabXai` 로그인 상태.
3. DOM에서 작성 대상을 못 찾으면 새 작업 탭에서 최대 3회까지 재시도한다. 게시 버튼을
   눌렀거나 결과가 애매하면 즉시 재게시하지 않고 Conversation API/DOM으로 기존 답글을
   찾는다. 확인되면 성공 처리, 미확인이면 `verification_required`로 보류한다.
4. 429·로그인 실패·페이지 오류는 X 전역 backoff로 격리한다. 품질이 좋은 초안은 폐기하지
   않고 재시도 가능 상태로 보존한다. 영구 금칙/중복/작성자 상한만 명시적으로 종료한다.
5. 모든 work tab·미디어 임시 파일·headless worker는 `finally`에서 회수하고, 시작 시
   지난 비정상 종료의 관리 프로세스와 임시물을 점검한다.

완료 조건: 게시 결과가 성공/재확인 필요/재시도 가능/영구 제외 중 하나로만 귀결되고,
동일 답글이 두 번 게시되지 않는다.

### 4. 대시보드와 운영 제어

1. 자동화 화면을 `수집 → Grok → Gemini → 게시 대기 → X 게시 → 완료/보류`로 표시한다.
   각 칸은 현재 건수, 가장 오래된 항목의 대기 시간, 최근 성공률/처리율, 마지막 KST 갱신
   시각을 보여 준다.
2. 전역 ON/OFF, 새 후보 수집 중지, 초안 생성만 허용(prefill-only), writer 일시정지,
   보류 재시도/폐기/수동 검수 동작을 분리한다. OFF는 진행 중인 X 게시를 취소하지 않고
   새 작업만 막는 의미로 고정한다.
3. 오류는 `수집`, `Grok`, `Gemini`, `품질`, `X UI`, `X 429`, `검증` 중 한 단계와
   재시도 예정 시각을 함께 표시한다. 이전 실행의 오류를 현재 병목처럼 표시하지 않는다.
4. 일일 목표, 실제 게시 수, 후보/검수 통과율, 작성자 분산, 429 횟수, Grok/Gemini 한도,
   p50/p95 단계별 지연을 추적한다.

완료 조건: 운영자가 대시보드만 보고 “왜 아직 게시되지 않았는지”, “언제 재시도되는지”,
“어느 단계가 느린지”를 알 수 있다.

### 5. 검증과 점진 롤아웃

1. 단위/계약 테스트: URL 정규화·중복 차단·KST 작성자 2건 상한·상태 전이·재시작 복원·
   재시도 분류·품질 게이트·오류 문자열의 게시 차단.
2. 통합 테스트: 5개 prefill worker가 서로 다른 문맥을 섞지 않고, Gemini가 뒤처져도
   다른 준비 항목과 writer가 막히지 않으며, writer는 항상 하나만 활성화되는지 검증한다.
3. 실제 E2E: Android share와 무관한 외부 자동댓글 경로에서, 9224의 `@terafabXai`
   로그인 확인 후 실제 writer 탭으로 대상 하나를 게시하고 reply URL/API/DOM 검증,
   탭·프로세스·임시 파일 회수까지 확인한다. 실제 게시 승인이 없는 환경에서는
   prefill-only와 writer 직전까지로 제한하고 E2E 미검증이라고 명시한다.
4. 롤아웃: `shadow(30건: 게시 없음) → 하루 소량(작성자별 1건) → 현재 2건 상한` 순서로
   진행한다. 각 단계는 품질 탈락 사유와 중복/429/게시검증 실패율이 기준 이하일 때만
   다음 단계로 간다. 기준 수치는 운영자가 승인한 값으로 문서화한다.

## 테스트 매트릭스

| 위험 | 자동 검증 | 운영 검증 |
| --- | --- | --- |
| 같은 글 재게시 | URL idempotency, 불확실 게시 복구 | reply URL 대조 |
| 한 계정 집중 | KST 2건 상한 + pending 예약 수 포함 | 작성자별 일일 집계 |
| 문맥 환각 | Grok 확인 필수, Gemini 최종 판정, 근거 게이트 | shadow 표본 수동 검수 |
| X UI/429 실패 | 3회 DOM 재시도, backoff, 재확인 상태 | 오류 화면 캡처·재시도 예정 |
| worker 병목 | 5개 준비 worker/단일 writer 계약 | 단계별 p95·queue age |
| 재시작/고아 프로세스 | 큐 복원·cleanup 테스트 | 서버 재시작 후 상태/프로세스 검사 |

## 최종 완료 기준

- 타인 원글만 후보로 삼고, 내 글 대댓글·Threads 예약 작업과 리소스/큐/상태가 섞이지 않는다.
- 문맥 없는 초안, 품질 탈락 초안, 실패 문자열, 중복 URL은 X에 게시될 수 없다.
- 작성자별 KST 2건 상한과 X 게시 단일 writer가 실제 상태와 테스트 모두에서 보장된다.
- 모든 보류/실패 항목은 이유·단계·재시도 시각·스크린샷(페이지 오류일 때)을 대시보드에서 확인할 수 있다.
- 자동 테스트와 승인된 실제 E2E가 통과하고, 롤아웃 단계의 운영 지표가 기준을 만족한다.
